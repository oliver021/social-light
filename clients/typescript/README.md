# socialLight — TypeScript client generation

Generates TypeScript types from each service's **OpenAPI** document. The C# typed
clients (`<Module>.Client`) are the shared artifact for .NET consumers; this is the
equivalent edge for the web/native TS frontends (DESIGN-STRATEGY.md §5/§7) — and it's
derived deterministically from the spec each service already publishes, not hand-written.

## OpenAPI endpoints

Every service exposes its document at `/openapi/v1.json` (enabled via the `OpenApi`
section in each `appsettings.json`; Scalar UI is at `/scalar` in Development). This
holds for the generated modules **and** the hand-written `Profile` / `Feed` services.

## Generate

```bash
# 1. Start the backend (cert-free http profile)
dotnet run --project src/SocialLight.AppHost --launch-profile http

# 2. Copy each service's URL from the Aspire dashboard into services.json
#    (ports are assigned dynamically), or set SOCIALLIGHT_OPENAPI_<NAME> env vars.

# 3. Generate
cd clients/typescript
npm install
npm run generate          # -> generated/<service>.ts
```

## Marketplace module (eShop store)

`catalog`, `ordering`, and `basket` are registered in `services.json` alongside the
social modules — the store is reused as the Marketplace module, so its typed client is
generated by the **same command**, no hand-writing.

- **`catalog`** publishes its OpenAPI host-free at build time
  (`Microsoft.Extensions.ApiDescription.Server` → `src/Catalog.API/Catalog.API.json`),
  so its spec is captured into `specs/catalog.json` and `generated/catalog.ts` exists.
- **`ordering` / `basket`** boot against Postgres/Redis/RabbitMQ, so they can't emit a
  spec host-free. Their specs are captured from a running host by the `OpenApiSpecDump`
  acceptance test (`dotnet test tests/SocialLight.AcceptanceTests -- --filter-method
  "*Dump_openapi_specs*"`), which boots the AppHost and writes every `specs/<name>.json`
  — `ordering` and `basket` included. Then `npm run generate` emits all 15 clients. This
  is the same deterministic path as the 12 social modules.

> Basket exposes the cart over **REST** (`Basket.API/Apis/BasketApi.cs`) in addition to
> its gRPC service precisely so it has an OpenAPI doc to generate a browser client from.

## Notes / next steps

- Today this emits **types** (request/response shapes). For full fetch clients, pair
  the generated types with `openapi-fetch` (same author) — a thin, typed wrapper.
- For a CI-friendly, no-running-server flow, enable build-time spec emission
  (`Microsoft.Extensions.ApiDescription.Server`) so each service writes its
  `*.json` at build, then point this generator at the files instead of URLs.
- All API calls go through the **`social-bff` gateway** (single origin); generated
  clients should target that base URL, not individual service ports.
