# CLAUDE.md — socialLight

socialLight presents itself as a full-featured social network (a Facebook-style
clone) **plus** a retained store / e-commerce module. Its architecture,
conventions, and patterns are deliberately modeled on the
[dotnet/eShop](https://github.com/dotnet/eShop) reference application. When in
doubt about *how* to build something here, look at how eShop does it and mirror
that approach.

This file is the authoritative design guide for anyone (human or agent) working
in this repo. See [REPO.md](REPO.md) for the catalog of product features, and
[`code-engine/DESIGN-STRATEGY.md`](code-engine/DESIGN-STRATEGY.md) for the
**canonical design of the generator and the module architecture it targets**.
That document is the source of truth for the code-generation strategy: where it
refines the specifics below — module-level specs, a single canonical form,
schema-per-module isolation, native-per-platform clients, the three artifact
categories — **it wins**.

> **Deployment:** the AppHost gateway needs `host.docker.internal`, so on native Linux
> Docker use the Compose stack in [`deploy/`](deploy/README.md) (see also README "Getting started").

## 0. What this project really is (read this first)

socialLight wears two hats, and it is important not to confuse them:

1. **The showcase (the "pretend").** On the surface this is an ambitious,
   production-grade social network with a built-in store. We build it out *as if*
   we were shipping it for real — advanced features, clean DDD/CQRS, the full
   eShop-style microservice topology. This is the demo that makes the experiment
   legible.

2. **The actual thesis (the "real key").** The point of socialLight is to be a
   **proof-of-concept for a deterministic code-generation engine** — the
   [`code-engine/`](code-engine) project at the repo root. The hypothesis: the
   large, *redundant* surface of a microservice app (the repetitive eShop-style
   vertical slice that every entity needs — model, EF context, minimal API,
   integration events, or a DDD aggregate + commands) should be produced by a
   **deterministic spec → template engine, not by LLM inference**. Inference is
   reserved for the genuinely novel parts; the boilerplate is generated.

   So the social network is, in large part, a *corpus of redundant code* that
   exercises and validates the engine. Every time you're about to hand-write a
   familiar slice, that's a signal it should come from `code-engine` instead.

**Practical consequence for anyone working here:** before writing the usual
per-entity boilerplate, check whether `code-engine` already generates it (see
§7 and [`code-engine/SKILL.md`](code-engine/SKILL.md)). Reach for inference only
for the parts the engine can't (or shouldn't) template.

> **Canonical design (read before extending the engine):** the full contract —
> the unit of generation is a **module** spec (not a single entity), the
> module-isolation invariants, the ports/adapters/bindings split, the three
> artifact categories (immutable / seed / manual-on-rails), and the
> native-per-platform client story — lives in
> [`code-engine/DESIGN-STRATEGY.md`](code-engine/DESIGN-STRATEGY.md). It
> supersedes the entity-level framing in this section and §7 where they differ;
> the current entity-level engine is the v0 step toward that contract.

### The eShop base IS the repo

The dotnet/eShop codebase is **not** a throwaway reference checkout — it is the
**working base** of socialLight. Its source has been moved to the **repo root**
(`src/`, `tests/`, `e2e/`, the solution files, etc.) and its `eShop` namespace
token has been **rebranded to `SocialLight`** (see §8, already applied). The
original nested `.git` was removed; this is now a single repository.

We extend that base in place: keep the e-commerce services as the store module,
and add social services alongside them (preferably generated by `code-engine`).

> **Milestone — the store is now the Marketplace module.** As of the marketplace
> integration, the eShop services (`Catalog.API`, `Ordering.API`, `Basket.API`,
> `OrderProcessor`, `PaymentProcessor`) are wired **into `SocialLight.AppHost`**
> and routed through `social-bff` — not run from the separate `LegacyEShop` host.
> They authenticate via the same `AddDefaultAuthentication` + `Identity__Audience=
> socialapi` binding every social module uses (`ValidateAudience=false`, so a token
> from the shared Identity is accepted; a user's `sub` is the buyer id). This is the
> deliberate counterpoint to code-engine: a rich, pre-existing DDD/CQRS domain is
> **reused wholesale**, never re-generated — generation is for redundant slices only.
> `LegacyEShop` is retained only as a standalone-store reference. Basket keeps its
> gRPC service for native/checkout callers AND exposes a REST adapter
> (`Basket.API/Apis/BasketApi.cs`, `Http1AndHttp2` on one port) over the same
> `IBasketRepository`, so the browser cart needs no gRPC-web — one repository, two
> transports, reading the buyer id from the JWT `sub`.
>
> **Scope: payment/checkout is intentionally left UNDONE.** The marketplace's value
> here is reusing a rich domain as *content* — so only `Catalog` browsing is in scope
> and e2e-tested. The payment path (Ordering order creation + Basket cart writes) is
> deliberately not built: those entry points throw an explicit `NotImplementedException`
> (`OrdersApi.CreateOrder(Draft)Async`, `BasketApi.Update/DeleteBasket`) pointing at the
> decision. Reads stay live. Don't "fix" these throws without resuming the payment work.

## 1. Guiding principles (inherited from eShop)

- **Services-based architecture orchestrated by .NET Aspire.** A single AppHost
  project wires up every service, database, cache, and message broker, and
  declares the dependencies between them. Local dev = run the AppHost.
- **Each service owns its data.** No shared database. Services communicate
  asynchronously through an event bus, never by reaching into each other's
  tables.
- **Vertical slices per service.** A service contains its own API, model,
  infrastructure, and integration events. This repetitive slice is exactly what
  `code-engine` generates — keep it uniform so the generator stays valid.
  Cross-cutting concerns live in shared projects (`ServiceDefaults`, `EventBus`,
  `Shared`).
- **Keep e-commerce — don't delete it.** The eShop e-commerce services
  (Catalog, Basket, Ordering, Payment, …) are **retained and expanded as the
  `store` / e-commerce module**, sitting next to the social modules. A social
  network with a marketplace/store is a feature, not legacy to remove.
- **Minimal APIs + API versioning + OpenAPI** for all HTTP endpoints.
- **DDD + CQRS where the domain is rich** (e.g. eShop's Ordering). Simpler
  services (e.g. eShop's Catalog) stay as straightforward CRUD/query services —
  don't over-engineer.
- **Async messaging via an integration event bus** (RabbitMQ) with the
  **transactional outbox** pattern (`IntegrationEventLogEF`) so domain state
  changes and published events are consistent.

> Rule of thumb: match the altitude of the eShop service that most resembles the
> one you're building. Rich, transactional, multi-step → follow `Ordering`.
> Read-heavy, mostly CRUD → follow `Catalog`. Ephemeral session state → follow
> `Basket` (Redis).

> **Refinement for *generated* modules ([DESIGN-STRATEGY.md](code-engine/DESIGN-STRATEGY.md) §1):**
> a machine needs one predictable target, so for new generated modules we
> deliberately diverge from eShop's internal inconsistency and emit a **single
> canonical module form**, with DDD ceremony as an explicit **opt-in** for rich
> domains — *"ceremony is proportional to domain complexity; the form is
> invariant."* The existing eShop services stay as the reference for the store
> module; the canonical form governs newly generated social modules.

## 2. Database: Postgres, not MSSQL

> **Important divergence from a "typical Microsoft stack."** Although socialLight
> targets the Microsoft/.NET stack (ASP.NET Core, EF Core, Aspire), our primary
> datastore is **PostgreSQL**, *not* SQL Server / MSSQL.
>
> This actually aligns with eShop, which also uses Postgres (the
> `ankane/pgvector` image — Postgres with vector search). Follow that lead:
>
> - Use **`Npgsql.EntityFrameworkCore.PostgreSQL`** as the EF Core provider.
> - Use **pgvector** for any embedding / semantic-search / recommendation
>   features (eShop uses it for AI catalog search; socialLight can use it for
>   content/friend recommendations and semantic search).
> - Each service registers its own `DbContext` against its own Postgres database
>   added in the AppHost (`postgres.AddDatabase("...")`).
> - EF Core migrations are owned by the service that owns the schema, and are
>   applied on startup via the shared `MigrateDbContextExtensions` helper.
> - Do **not** introduce `Microsoft.EntityFrameworkCore.SqlServer` or MSSQL
>   containers. If you see MSSQL referenced anywhere, treat it as a mistake to
>   migrate to Postgres.

> **Refinement ([DESIGN-STRATEGY.md](code-engine/DESIGN-STRATEGY.md) §4):**
> "each service owns its data" is enforced as **schema-per-module** with **no
> cross-module foreign keys, JOINs, or cross-table queries** — cross-module data
> flows only through events (`publishes`/`consumes`). Physically this may be a
> single Postgres instance; logical isolation is what matters, so a module can
> later move to its own database without breaking anything. The connection
> (pool, engine, resilience) is a **binding** provided **once by the host**
> composition root; the module sees only its injected `DbContext` and its ports
> — never `Npgsql` or a connection string.

## 3. Solution layout (extend eShop's `src/`)

The eShop projects under `src/` are **kept**. The e-commerce ones become the
**store module**; the social modules are **added alongside** them using the same
patterns (ideally generated by `code-engine`). The `eShop` namespace token has
been rebranded to `SocialLight` (§8), but project roles are unchanged.

| eShop project (kept)     | Role / pattern                                      | Becomes / sits beside                          |
|--------------------------|-----------------------------------------------------|------------------------------------------------|
| `eShop.AppHost`          | .NET Aspire orchestration of everything             | `SocialLight.AppHost` (orchestrates all modules)|
| `eShop.ServiceDefaults`  | Shared host setup: telemetry, health, auth, OpenAPI, resilient HTTP | `SocialLight.ServiceDefaults` (shared) |
| `Identity.API`           | Duende IdentityServer / OIDC auth provider          | shared auth for both store + social            |
| `Catalog.API`            | CRUD + query service, OpenAPI, pgvector search      | **store module**; pattern for `Profile.API`, `Posts.API` |
| `Basket.API`             | Redis-backed ephemeral state, gRPC + events         | **store cart**; pattern for `Notifications`, `Presence` |
| `Ordering.API`           | Rich DDD + CQRS + MediatR + outbox                  | **store checkout/orders**; pattern for `Social.API` (friendships, groups) |
| `Ordering.Domain`        | Aggregates, entities, value objects, domain events  | store domain; pattern for `Social.Domain`      |
| `Ordering.Infrastructure`| EF Core persistence for the domain                  | store persistence; pattern for `Social.Infrastructure` |
| `OrderProcessor`         | Background worker consuming integration events      | store worker; pattern for `FeedProcessor`, `TimelineProcessor` |
| `PaymentProcessor`       | Background worker (grace-period / external system)  | store payments; pattern for `MediaProcessor`   |
| `Webhooks.API` / `WebhookClient` | Outbound webhook subscriptions + sample client | shared, used by both modules           |
| `EventBus` / `EventBusRabbitMQ` | Integration event abstractions + RabbitMQ impl | reuse as-is (shared)                    |
| `IntegrationEventLogEF`  | Transactional outbox for reliable publishing        | reuse as-is (shared)                           |
| `WebApp`                 | Blazor Server storefront UI                         | hosts both the store UI and the social UI      |
| `WebAppComponents`       | Shared Razor components / API clients               | shared components/clients                       |
| `HybridApp` / `ClientApp`| .NET MAUI mobile/hybrid client                      | `MobileApp`                                     |
| `mobile-bff` (YARP)      | Backend-for-frontend reverse proxy                  | `mobile-bff` (routes store + social)           |
| `Shared`                 | `MigrateDbContextExtensions`, activity helpers      | reuse as-is (shared)                           |

> **New social services should be scaffolded with `code-engine`, not hand-typed.**
> Pick the matching preset: `simple-service` (Catalog-style CRUD) or
> `rich-domain` (Ordering-style DDD). See §7.

> **Frontend direction ([DESIGN-STRATEGY.md](code-engine/DESIGN-STRATEGY.md) §5 & §7):**
> because a *generator*, not a human, writes the UI scaffolding, we flip eShop's
> reuse-driven trade-off and target **native per platform** (MAUI native + web)
> rather than a shared hybrid WebView. The one shared, generated artifact is the
> set of **typed API clients**, which every client — and every hand-built page —
> consumes. Feeds and profiles are **not** generated: they are hand-built "on
> the rails" the generator lays (category 3 below), plugging into the same typed
> clients as a generated CRUD page would.

## 4. Key patterns to follow

### 4.1 AppHost orchestration (`src/*.AppHost/Program.cs`)
Declare infra first (`redis`, `eventbus`/RabbitMQ, `postgres` with pgvector),
add one database per service, then add each project with `.WithReference(...)`
and `.WaitFor(...)` to express dependencies. External-facing apps get
`.WithExternalHttpEndpoints()`. Cross-service callback URLs are wired through
`.WithEnvironment(...)`. Health checks via `.WithHttpHealthCheck("/health")`.

### 4.2 Service bootstrap (`Program.cs` per service)
```
builder.AddServiceDefaults();          // telemetry, health, service discovery, resilience
builder.AddApplicationServices();      // DI registrations in Extensions/Extensions.cs
builder.Services.AddProblemDetails();
var withApiVersioning = builder.Services.AddApiVersioning(...);
builder.AddDefaultOpenApi(withApiVersioning);
var app = builder.Build();
app.MapDefaultEndpoints();
app.MapXxxApi();                       // minimal-API endpoint group
app.UseDefaultOpenApi();
app.Run();
```
Keep `Program.cs` thin. DI wiring lives in `Extensions/Extensions.cs`
(`AddApplicationServices`). Endpoints are grouped in `Apis/XxxApi.cs` as minimal
APIs, with the handler logic in a paired `XxxServices.cs`.

### 4.3 Rich domain services — DDD + CQRS (model: `Ordering`)
- **Domain** project: `AggregatesModel/<Aggregate>/` (root entity + `IRepository`),
  `SeedWork/` (`Entity`, `ValueObject`, `IAggregateRoot`, `IUnitOfWork`),
  `Events/` (domain events), `Exceptions/`. Aggregates raise domain events;
  business rules live in the aggregate, not in handlers.
- **Application** layer (inside the `.API`): `Commands/` + handlers,
  `Queries/`, `Behaviors/` (MediatR pipeline: logging, validation, transaction),
  `Validations/` (FluentValidation), `DomainEventHandlers/`,
  `IntegrationEvents/` (EventHandling + Events).
- Use **MediatR** for commands/queries and domain-event dispatch.
- The **`IdentifiedCommand`** wrapper provides request idempotency — reuse it.

### 4.4 Simple services — CRUD + queries (model: `Catalog`)
No MediatR, no aggregates. EF Core `DbContext` + minimal-API handlers directly,
DTOs in `Model/`, integration events in `IntegrationEvents/`, optional pgvector
semantic search in `Services/`.

### 4.5 Messaging & the outbox
- Define integration events as records extending the `EventBus` base event.
- Publish through the event bus; persist them in the same DB transaction via
  `IntegrationEventLogEF` (transactional outbox), then relay to RabbitMQ.
- Consumers implement `IIntegrationEventHandler<T>` and subscribe in DI.
- Never call another service synchronously to mutate state — emit an event.

### 4.6 Auth
`Identity.API` is the OIDC/IdentityServer authority. Services validate JWTs via
`ServiceDefaults` `AuthenticationExtensions`. Read the user via
`ClaimsPrincipalExtensions`. The web/mobile clients use the BFF + OIDC flow.

## 5. Conventions

- **.NET 10** (SDK pinned in `global.json`), C# latest, nullable enabled,
  `GlobalUsings.cs` per project.
- Central package management: `Directory.Packages.props`; shared MSBuild config
  in `Directory.Build.props` / `.targets`. Add NuGet versions there, not in csproj.
- One responsibility per project; cross-cutting code goes to a `Shared`/
  `ServiceDefaults`/`EventBus` project, not copied around.
- All services expose `/health` and OpenTelemetry traces/metrics via
  `ServiceDefaults` — don't hand-roll observability.
- Tests live under `tests/`; integration tests use the Aspire test host and the
  `Program.Testing.cs` partial. E2E uses Playwright (`e2e/`, `playwright.config.ts`).

## 6. Working in this repo

- **Run everything:** start the AppHost project; the Aspire dashboard shows all
  services, logs, and traces.
- **Add a new service:** prefer `code-engine` (§7). Write an entity spec, pick a
  preset, generate the slice, then add the service to the AppHost with its
  Postgres database and event-bus reference. Only fall back to hand-copying an
  eShop analogue when the engine can't express what you need.
- **The eShop base** is the repo itself: its services live under `src/` (rebranded
  to `SocialLight`). The e-commerce services are the store module; read any of
  them for a pattern you're unsure about.

## 7. code-engine — the deterministic generator (the experiment)

[`code-engine/`](code-engine) is the heart of the project (see §0). It is a
small Node/Nunjucks tool that renders the full eShop-style vertical slice of
`.cs` files from a spec — deterministically, no inference.

- **Design contract (read first):**
  [`code-engine/DESIGN-STRATEGY.md`](code-engine/DESIGN-STRATEGY.md) is the
  authoritative design for the generator and the module architecture it targets:
  the canonical module form, the spec grammar, the isolation invariants, the
  rendering algorithm, and the writing rules. Conform to it when extending the
  engine.
- **Operational how-to:** [`code-engine/SKILL.md`](code-engine/SKILL.md)
  documents how to run the tool as it exists today.
- **Current state vs target:** the tool today takes an **entity-level** spec and
  ships two presets (`simple-service`, `rich-domain`). The canonical target is a
  **module-level** spec (`module` + `entities[]` + `publishes`/`consumes`)
  rendered across **module / entity / platform** scopes
  (`template + spec + scope = source(s)`) into a single canonical form. Treat the
  entity-level engine as the v0 step toward that contract.

- **Two presets**, matching the two service patterns above:
  - `simple-service` → Catalog-style CRUD (`Model/`, `Infrastructure/`,
    `Apis/`, `IntegrationEvents/`).
  - `rich-domain` → Ordering-style DDD (`AggregatesModel/<Entity>Aggregate/`,
    `Application/Commands/`).
- **Run it (from `code-engine/`):**
  ```powershell
  npm install                       # one time
  node src/index.js generate <spec.json> --out <target-dir> [--dry-run] [--force]
  node src/index.js list-presets
  ```
- **Three artifact categories (the writing discipline — DESIGN-STRATEGY.md §6 & §8):**
  (1) *generated & immutable* — always overwritten, never hand-edited (entities,
  repos, `DbContext`, typed clients, CRUD pages); (2) *seed* — generated once,
  then yours to own (nav shell, containers); (3) *manual on generated rails* —
  never generated, hand-built against the typed clients (feed, profile,
  onboarding). The seam between generated and manual code **relies on** the
  ports; it does not break them.
- **Extend it, don't bypass it.** New output file → add a `.njk` to a preset
  folder (filenames use `__Entity__`, `__event__`, … tokens). New pattern → add
  a folder under `templates/`. Project-wide type shortcuts / custom filters live
  in [`code-engine.config.js`](code-engine/code-engine.config.js).
- **Rule:** if you're about to type a slice that looks like one the engine
  already emits, generate it instead and only edit the genuinely novel parts.

## 8. Rebranding the eShop base (`eShop` → `SocialLight`) — applied

Because we build on the eShop codebase, the `eShop` namespace token was rebranded
to `SocialLight`. This is a deterministic, redundant transformation (the same
spirit as code-engine) handled by scripts, not by hand or by inference. **It has
already been applied** to the tree under `src/`. Two scripts exist:

- [`scripts/Rebrand-Solution.ps1`](scripts/Rebrand-Solution.ps1) — the **full
  rebrand**. Rewrites the token in *all* code/build/solution/config files
  (`.cs`, `.csproj`, `.slnx`, `.slnf`, `.props`, `.proto`, `.xaml`, `.razor`,
  `.json`, `.yml`, …) **and renames files/folders** (`eShop.AppHost` →
  `SocialLight.AppHost`, `eShop.slnx` → `SocialLight.slnx`, etc.). Preserves
  UTF-8 BOM + CRLF. Preview by default; pass `-Apply` to write.
  - Deliberately left alone for attribution: markdown docs (`*.md`), `LICENSE`,
    the `img/` screenshots, and the upstream `github.com/dotnet/eShop` URLs.
- [`scripts/Rename-Namespaces.ps1`](scripts/Rename-Namespaces.ps1) — the narrow
  tool: `.cs` namespace/using declarations only. Kept for targeted use; use
  `-WhatIf` to preview.

> If you ever pull more files from upstream eShop, re-run
> `Rebrand-Solution.ps1 -Apply` to normalize them.
